# 风险评分配置指南

## 📊 评分模式说明

系统支持两种风险评分模式，你可以根据团队习惯选择：

### 🔒 安全模式（Safety Mode，默认）

**分数越低越安全**，符合"安全评分"的直观认知。

```
0-20 分：   🔴 危急      (Critical - 非常不安全)
20-40 分：  🟣 高风险    (High Risk)
40-60 分：  🟠 中风险    (Medium Risk)
60-80 分：  🟡 低风险    (Low Risk)
80-100 分： 🟢 安全      (Safe)
```

**示例：**
- 安全评分 16.63 → 🔴 危急（系统非常不安全，需要立即处理）
- 安全评分 35.50 → 🟣 高风险（存在较多安全问题）
- 安全评分 75.30 → 🟡 低风险（系统比较安全）
- 安全评分 92.30 → 🟢 安全（系统非常安全）

**适用场景：**
- ✅ 安全评分（分数越高越安全，符合直觉）
- ✅ 健康度评分（分数越高越健康）
- ✅ 向非安全背景的管理层汇报
- ✅ 安全成熟度评估

---

### ⚠️ 威胁模式（Threat Mode，可选）

**分数越高越危险**，符合 CVSS、NIST 等安全标准。

```
0-20 分：   🟢 安全      (Safe)
20-40 分：  🟡 低风险    (Low Risk)
40-60 分：  🟠 中风险    (Medium Risk)
60-80 分：  🟣 高风险    (High Risk)
80-100 分： 🔴 危急      (Critical)
```

**示例：**
- 威胁评分 16.63 → 🟢 安全（几乎没有漏洞）
- 威胁评分 75.50 → 🟣 高风险（需要立即处理）
- 威胁评分 92.30 → 🔴 危急（系统已被入侵）

**适用场景：**
- ✅ 向专业安全团队汇报（符合行业标准）
- ✅ 漏洞优先级排序（高分优先处理）
- ✅ 合规审计（符合 CVSS 标准）
- ✅ 与第三方安全工具对接

## ⚙️ 配置方法

### 方法 1: 通过 test_input.json 配置

```json
{
    "target": "http://example.com",
    "test_mode": "full",
    "time_limit": 120,
    "report_format": "html",
    "score_mode": "safety"  // 默认：safety（分数越低越安全）
}
```

### 方法 2: 通过命令行参数配置

```bash
# 使用安全模式（分数越低越安全，默认）
python main.py '{"target": "http://example.com", "score_mode": "safety"}'

# 使用威胁模式（分数越高越危险）
python main.py '{"target": "http://example.com", "score_mode": "threat"}'
```

### 方法 3: 通过 OpenClaw 配置

在飞书中测试时，可以在指令中包含配置：

```
帮我测试 http://example.com，使用安全模式评分
```

或在 `custom_options` 中指定：

```json
{
    "target": "http://example.com",
    "custom_options": {
        "score_mode": "safety"  // 或 "threat"
    }
}
```

### 方法 4: 修改默认配置

编辑 [`main.py`](file://d:\TRAE\advanced-pentester-v1.2\intelligent-test-orchestrator\main.py#L300)，修改默认值：

```python
# 默认使用威胁模式（分数越高越危险）
score_mode = config.get('score_mode', 'threat')  # 推荐

# 或改为安全模式（分数越低越安全）
score_mode = config.get('score_mode', 'safety')  # 旧版兼容
```

## 📈 评分计算逻辑

### 风险评估维度

风险评分基于以下四个维度加权计算：

| 维度 | 权重 | 评估内容 |
|------|------|----------|
| **技术栈风险** | 40% | 技术版本、CVE 数量、已知漏洞 |
| **暴露面风险** | 30% | 端口数量、服务复杂度、认证要求 |
| **业务风险** | 20% | 业务类型、数据敏感性 |
| **配置风险** | 10% | 安全配置、Headers、SSL/TLS |

### 计算公式

```python
overall_score = (
    tech_risk * 0.4 +       # 技术栈风险
    exposure_risk * 0.3 +   # 暴露面风险
    business_risk * 0.2 +   # 业务风险
    config_risk * 0.1       # 配置风险
)
```

### 业务类型风险系数

不同业务类型有不同的基础风险系数：

| 业务类型 | 风险系数 | 说明 |
|----------|----------|------|
| 银行/金融 | 1.5x | 最高风险等级 |
| 医疗健康 | 1.4x | 敏感数据多 |
| 政府系统 | 1.3x | 安全要求高 |
| 电子商务 | 1.2x | 交易数据 |
| 社交网络 | 1.1x | 用户数据 |
| 教育 | 1.0x | 标准风险 |
| 企业门户 | 0.9x | 相对较低 |
| CMS | 0.8x | 内容管理 |
| 个人网站 | 0.7x | 最低风险 |

## 🎯 实际案例对比

### 案例 1: 小型企业网站

**测试结果：**
- 发现 5 个低危漏洞
- 技术栈：WordPress 5.8（有已知 CVE）
- 暴露面：80, 443 端口
- 业务类型：CMS

**威胁模式评分：** 35.2 分 → 🟡 低风险

**安全模式评分：** 64.8 分 → 🟡 低风险

**结论：** 两种模式结论一致，但表达方式不同。

---

### 案例 2: 金融系统

**测试结果：**
- 发现 15 个漏洞（3 个高危，5 个中危）
- 技术栈：老旧 Java 应用 + 过期组件
- 暴露面：多个 API 端点，弱认证
- 业务类型：Financial

**威胁模式评分：** 78.5 分 → 🟣 高风险

**安全模式评分：** 21.5 分 → 🔴 危急

**结论：** 威胁模式更直观（高分=高危），安全模式容易误解。

---

### 案例 3: 个人博客

**测试结果：**
- 发现 2 个信息泄露
- 技术栈：最新静态网站生成器
- 暴露面：仅 443 端口
- 业务类型：Personal

**威胁模式评分：** 12.3 分 → 🟢 安全

**安全模式评分：** 87.7 分 → 🟢 安全

**结论：** 两者都能正确反映低风险状态。

## 🔄 迁移建议

### 从安全模式迁移到威胁模式

如果你之前使用的是安全模式（分数越低越安全），建议迁移到威胁模式：

**优点：**
- ✅ 符合 CVSS、NIST 等行业标准
- ✅ 更直观（高分=高危）
- ✅ 便于与管理层和安全团队沟通
- ✅ 漏洞优先级更清晰

**迁移步骤：**

1. **修改配置文件**
   ```json
   {
       "score_mode": "threat"
   }
   ```

2. **更新报告模板**
   - 修改风险等级描述
   - 调整颜色映射（红=高危，绿=安全）

3. **培训团队成员**
   - 解释新的评分逻辑
   - 提供评分对照表

4. **历史数据对比**
   - 旧分数 = 100 - 新分数
   - 例如：旧 80 分（安全）= 新 20 分（安全）

## 🎓 常见问题

### Q1: 为什么默认使用威胁模式？

**A:** 威胁模式（分数越高越危险）是安全行业的标准做法：
- CVSS 评分系统（0-10 分，越高越严重）
- NIST 风险框架
- OWASP 风险评级

### Q2: 能否同时使用两种模式？

**A:** 可以！不同目标可以使用不同模式：

```json
{
    "targets": [
        {"url": "http://example1.com", "score_mode": "threat"},
        {"url": "http://example2.com", "score_mode": "safety"}
    ]
}
```

### Q3: 如何向管理层解释评分？

**A:** 使用威胁模式 + 简单类比：

> "风险评分就像体温计：
> - 36°C（0-20 分）：正常，很健康
> - 38°C（20-40 分）：低烧，需要注意
> - 39°C（40-60 分）：中烧，需要休息
> - 40°C（60-80 分）：高烧，需要看医生
> - 42°C（80-100 分）：危险，需要急救"

### Q4: 评分达到多少需要立即处理？

**A:** 建议阈值：
- 🔴 **80+ 分**：立即响应（2 小时内）
- 🟣 **60-80 分**：24 小时内处理
- 🟠 **40-60 分**：7 天内处理
- 🟡 **20-40 分**：30 天内处理
- 🟢 **0-20 分**：定期监控
