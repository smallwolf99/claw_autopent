🔴 核心漏洞发现汇总

1. 漏洞名称：SQL 注入 (UNION-based & 盲注)

  • 漏洞地址: http://172.16.8.151:4280/vulnerabilities/sqli/
  • 风险等级: 🔴 严重 (Critical)
  • 发现时间: 2026-04-22 11:45
  • PoC验证: id=1' UNION SELECT user,password FROM users--
  • 验证结果: ✅ 成功提取所有用户的MD5密码哈希(admin: 5f4dcc3b5aa765d61d8327deb882cf99)；并验证了Boolean-based和Time-based盲注的可行性。
  • 影响: 数据库完全暴露，所有敏感数据泄露，可能进一步导致服务器控制。
  • 修复建议: 必须使用参数化查询(Prepared Statements)或PDO处理所有的数据库输入；避免拼接SQL字符串。

2. 漏洞名称：操作系统命令注入

  • 漏洞地址: http://172.16.8.151:4280/vulnerabilities/exec/
  • 风险等级: 🔴 严重 (Critical)
  • 发现时间: 2026-04-22 11:47
  • PoC验证: ip=127.0.0.1|id
  • 验证结果: ✅ 成功执行系统命令，获取当前用户身份为 uid=33(www-data) gid=33(www-data)。
  • 影响: 攻击者可执行任意操作系统命令，完全控制Web服务器。
  • 修复建议: 尽量避免使用系统命令；如果必须使用，应使用白名单严格限制输入，并使用 escapeshellarg() 或 escapeshellcmd() 等函数进行转义。

3. 漏洞名称：任意文件上传导致RCE

  • 漏洞地址: http://172.16.8.151:4280/vulnerabilities/upload/
  • 风险等级: 🔴 严重 (Critical)
  • 发现时间: 2026-04-22 11:48
  • PoC验证: 上传包含 <?php echo "TEST_UPLOAD_SUCCESS"; ?> 的 test_upload.php 文件。
  • 验证结果: ✅ 文件成功上传至 /hackable/uploads/ 目录并且可被解析执行。
  • 影响: 攻击者可上传WebShell(如一句话木马)，直接获取服务器的完全控制权。
  • 修复建议: 严格验证文件MIME类型和扩展名（白名单）；上传目录取消执行权限；重命名上传文件并隐藏真实路径。

4. 漏洞名称：本地文件包含 (LFI)

  • 漏洞地址: http://172.16.8.151:4280/vulnerabilities/fi/
  • 风险等级: 🔴 严重 (Critical)
  • 发现时间: 2026-04-22 11:47
  • PoC验证: page=../../../../../../etc/passwd
  • 验证结果: ✅ 成功读取服务器的 /etc/passwd 和 /etc/hosts 敏感文件。
  • 影响: 泄露服务器敏感配置文件、源码，可能结合日志投毒(Log Poisoning)导致远程代码执行(RCE)。
  • 修复建议: 使用白名单限制可包含的文件列表；禁止使用用户可控的输入直接构建文件路径；禁用不必要的远程文件包含配置(allow_url_include)。

5. 漏洞名称：不安全的验证码逻辑绕过

  • 漏洞地址: http://172.16.8.151:4280/vulnerabilities/captcha/
  • 风险等级: 🔴 严重 (Critical)
  • 发现时间: 2026-04-22 12:30
  • PoC验证: 拦截请求，直接发送带有 step=2 的POST请求。
  • 验证结果: ✅ 无需任何有效的验证码Token，即可直接完成第二步，成功修改密码。
  • 影响: 验证码机制完全形同虚设，防自动化攻击功能失效。
  • 修复建议: 在最终执行敏感操作(如修改密码)时，必须再次校验验证码状态；不能依赖客户端传递的"步骤"参数。

6. 漏洞名称：多形态跨站脚本 (XSS)

  • 漏洞地址: /vulnerabilities/xss_r/, /xss_d/, /xss_s/
  • 风险等级: 🟠 高危 (High)
  • 发现时间: 2026-04-22 11:46 - 12:31
  • 验证结果: ✅ 反射型、DOM型、存储型XSS全部验证成功。其中Stored XSS成功插入了恶意图片标签并触发脚本执行。
  • 影响: 窃取管理员/用户会话Cookie，实施钓鱼攻击，甚至接管其他用户账户。
  • 修复建议: 对所有不受信任的数据在输出到HTML前进行严格的实体编码(如使用 htmlspecialchars())；配置强力的Content-Security-Policy (CSP)。
